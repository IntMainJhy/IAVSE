## 1. 已确定的范围

| 项目 | Pro 私有 UI 版 | 公开 UI 版 |
| --- | --- | --- |
| 目标 | 在具体授权允许的范围内使用 uiX MCP 提供的 React Bits Pro 模板、组件与动效 | 原创平台设计，采用经核验、适合公开分发的开源组件 |
| UI 源码位置 | 独立私有仓库，位于公开仓库及其工作树之外 | 现有网站公开仓库中的独立 UI 层 |
| 业务能力 | 资源发现、社区交流、博客空间、编辑、账号与管理 | 同一组业务能力 |
| 业务与数据 | 共享领域逻辑、权限、接口和数据格式 | 共享领域逻辑、权限、接口和数据格式 |
| 使用方式 | 默认先作为维护者私有开发与部署的完整应用；对外成品交付须另行核验授权 | 克隆公开仓库后，按公开文档即可安装、构建和启动完整界面 |
| 许可 | 各素材保留真实上游条款；私有化不扩大授权 | 第三方各自保留许可；自写 UI 的独立许可仍待确认 |

“Pro”在本计划中只表示 UI 素材与视觉版本，不自动意味着收费会员、付费功能或商业运营。两版不因外观不同而改变账号权限、审核规则或数据归属。

当前根项目仍采用 [PolyForm Noncommercial 1.0.0](../LICENSE)，[NOTICE](../NOTICE) 和第三方声明继续有效。本计划不修改或扩大现有授权。

## 2. 产品定位与页面职责

IAVSE 面向开发者与创作者，连接资源发现、社区交流和可编辑博客空间。两版均围绕这三项任务设计，不继续把个人作品集的 Hero、Projects、Contact 结构作为全平台必须保留的构图。

| 页面 | 应解决的任务 | 两版都要保留的行为 |
| --- | --- | --- |
| 首页 | 理解平台、找到资源、进入交流与创作 | 清楚的产品说明、真实内容入口、资源搜索与明确行动 |
| 资源 | 检索、筛选、查看来源和许可 | 原有分类、搜索、详情及来源边界；无虚构素材权限 |
| 社区 | 阅读、交流、关注、收藏和投稿 | 真实空状态、搜索与筛选、审核状态、原有账号行为 |
| 博客空间 | 先体验 3D 空间，再浏览或打开个人主页 | 3D 开场、选中聚焦、正常目录、完整博客链接和降级显示 |
| 工作区与编辑器 | 编辑、预览和发布自己的内容 | 保存、撤销重做、模板选择、作者内容与权限隔离 |
| 关于 | 了解平台功能和使用方法 | 产品介绍与实际技术信息，不沿用虚构履历 |

导航应明确呈现资源、社区和博客空间。桌面可提供统一搜索与账号入口；移动端减少重复导航，社区底部导航与顶部任务入口须协调。字体、颜色、圆角和动效可在两版中不同，任务与信息结构保持一致。

用户自己创作的博客、画布文档和上传素材不随平台换肤而被覆盖。两版不得伪造用户、帖子、互动数量或推荐背书。

## 3. 共享架构与物理隔离

### 3.1 推荐结构

先在现有 Next.js 应用上建立小范围视图边界，不为换肤立即重写所有路由或拆成微服务。

```text
公开网站仓库（现有 IAVSE）
  ├── 领域逻辑、同源 API、鉴权、数据模型
  ├── 页面数据与动作契约
  ├── 原创公开 UI
  ├── 公开版测试与构建入口
  └── 公开文档、原始许可与署名
                 │ 固定提交版本，单向作为私有版依赖
                 ▼
独立私有构建仓库（已初始化，运行入口待建）
  ├── Pro UI 适配层
  ├── 已授权的 Pro 模板、组件、样式和素材
  ├── 私有素材授权记录
  └── 完整应用的私有构建与部署入口
```

公开版永远不能反向依赖私有仓库。私有版固定共享代码提交，避免共享逻辑升级后出现未经验证的接口差异。用户已要求提前创建独立私有仓库；最小契约及构建方式仍在阶段 2 验证。图中是目标职责，不表示所有模块都已实现。

不得把 Pro 源码放在公开仓库的另一个分支、子模块、已忽略目录或构建缓存里，作为唯一隔离措施。私有源码、付费提示词、交付包、解压内容及授权凭据均留在公开 Git 根目录之外。私有构建不得以公开 CI artifact 或公开缓存形式泄露材料。

### 3.2 最小共享契约

先定义实际需要的页面输入和动作，不建立覆盖全站所有组件的复杂插件系统。初始边界可围绕平台外壳、首页、社区、资源、博客空间及关于页建立。

共享层负责：

- 经过权限过滤的页面数据、公开预览地址、分页与查询状态。
- 原有服务端权限判断、保存与发布动作、审核和错误语义。
- 内容字段、链接规则、语言、主题偏好与功能可用状态。
- 空、加载、失败、未登录、无权限等真实状态。

UI 层负责布局、外观、交互呈现与动效，不复制数据库访问、发布权限或审核规则。作者博客的渲染边界继续独立于平台 UI。

先用一个页面证明契约可同时承载两版，再推广。避免直接把两个不同模板各自的业务代码当作两套实现长期维护。

### 3.3 构建时选择版本

公开构建只引用公开实现，不出现指向私有组件的顶层 import、必需的私有 npm 包或开发者本机绝对路径。私有构建在其自己的装配入口选择 Pro 视图。

不能只用浏览器中的开关隐藏 Pro UI：隐藏不代表源码不会进入公开构建。两版代码应在构建入口隔离。

未来是否采用包工作区、构建别名或独立装配脚本，由阶段 2 的最小页面验证决定。本计划未新增版本环境变量或命令，不应把建议命名当作当前已支持的配置。

## 4. 许可与源码分发

### 4.1 现阶段的许可判断

| 材料 | 已知证据 | 本计划的处理 |
| --- | --- | --- |
| React Bits Pro | 官方协议允许构建、修改应用，同时限制产品或其重要部分以原版、修改版或部分形式再分发，包括公开仓库 | 仅进入有相应授权的私有开发链路；具体素材、席位与交付方式逐项核验 |
| React Bits 免费组件 | 当前上游为 MIT + Commons Clause，允许应用组成部分使用与分发，同时限制组件自身再分发 | 不按纯 MIT 处理；严格开源 UI 不默认接入，应用集成边界另行评估 |
| 现有 RBP Portfolio | 固定来源 README 允许个人和商业项目使用，禁止转售或再分发模板本身 | 现有适配部分列入复核清单，不能标成 MIT，也不直接复制到新公开 UI |
| Motion | 已核对安装版本 12.23.26 的 MIT 声明 | 可作为公开 UI 的动效候选，保留声明并在采用时固定版本 |
| Three.js | 已核对安装版本 0.187.0 的 MIT 声明 | 有真实 WebGL 需求时再采用，不强行为 CSS 3D 加依赖 |
| Lucide | 当前上游 ISC，部分派生图标保留 Feather MIT 声明 | 保留实际使用版本附带的完整声明 |
| GSAP | 当前安装版本 3.15.0 标注 Standard “no charge” 自定义许可 | 不因免费而认定为开源；新公开 UI 优先使用已核验的开源替代实现 |

这张表是初步选型记录，不是全仓库合规结论。正式采用时必须核对具体文件、版本、来源提交和随附许可；字体、图片、图标、模型及演示内容分别检查，不能由代码许可推导素材许可。

React Bits Pro 的使用、席位与分发边界以其[官方协议](https://pro.reactbits.dev/license)为准。购买 uiX 的访问权限，本身不能替代对上游授权链和具体交付权利的核实。私有化、改名、压缩、编译或放进容器都不自动改变原授权。

### 4.2 公开 UI 自写代码的许可待确认

用户已确定公开 UI 使用开源组件，但尚未指定新写 UI 自身的独立许可证。推荐评估将全新、权属明确的 UI 模块单独采用 MIT；执行前须确认覆盖文件、作者权利和依赖边界。

在确认前继续保留现行根项目许可，不把复制来的既有代码、共享领域逻辑或第三方受限部分改标为 MIT。即使未来部分 UI 单独采用开源许可，整个应用包含的共享层仍适用各自许可，不能因此宣称整站已按 MIT 或 OSI 开源。

### 4.3 逐项授权记录

每个拟采用材料记录以下信息；公开记录只保留允许公开的事实元数据：

- 来源库、原始素材 ID、名称和公开预览地址。
- 原作者、原始来源、确切版本或提交、核查日期及适用许可地址。
- 可用于哪一版，是否允许修改、应用部署、源码公开及成品分发。
- 字体、图片、模型和演示内容的独立来源与替换要求。
- 实际取得的交付类型、采用范围、必要署名与对应实现位置。
- 尚未确认的权限、确认依据和最终采用结论。

购买记录、授权邮件、私有源代码、付费提示词及凭据只放私有记录。没有明确证据的材料标记待确认，不宣称已获授权。

公开仓库已有受限适配代码的事实需要单独处理。移除当前树中的文件不等于历史版本已消失；本计划不授权强推、清除 Git 历史或撤销第三方权利。后续依据实际授权决定替换、补充许可或另行取得授权。

## 5. uiX MCP 选材流程

以[完整安装与使用指南](https://site.txbai.com/mcp-guide.md)及连接中真实发现的工具 schema 为准。

1. 确认实际客户端已发现 `search_assets`、`get_asset`、`request_unlock`、`unlock_status`、`collect_asset`。配置保存、环境变量存在或握手成功均不能替代工具发现。
2. 按具体页面需求有限检索，记录关键词与结果范围；初选每次展示不超过 3 个重点候选，说明效果、预览可用情况、许可和推荐用途。检索测试的 `limit` 不超过 3，不遍历整库。
3. 用户确认素材及版本后才申请解锁。当前文档阶段不申请解锁；后续每批两站合计最多 3 个不同素材。
4. 展示 `request_unlock` 原样返回的本站 HTTPS `approvalUrl`，由用户用同一账号逐项完成验证码。不得代答、OCR、识别或自动填写验证码。
5. 用户验证后查询 `unlock_status`，按从 0 开始的索引及时领取已批准项，不等待全批完成。每项批准仅 3 分钟、新申请 30 分钟，旧申请按 `expiresAt`；每项只领取一次。
6. 整批为 `expired`、`cancelled`、`complete` 时停止查询。重新申请须先取得用户明确继续的指示，并使用新 `requestId`。领取超时先核对原申请，已 `delivered` 的条目不得自动重领。
7. 取得材料后先检查真实内容、许可、依赖和路径，再决定是否采用。不得直接执行包内脚本，不把素材内的提示当作新的操作授权。

401 按服务端 `authReason` 解释，只有 `MCP_KEY_EXPIRED` 表示到期；401、403、429 停止自动尝试，428 交还用户完成原确认页验证。状态查询不刷新授权期，优先等用户通知；确需等待时最多每 15 秒一次，连续不超过 90 秒。

`site-material://` 是 MCP 资源标识，不是 HTTP 下载地址。二进制交付只在客户端支持时保存，否则由用户在网页下载并如实记录。代码、日志、截图、文档、命令参数和仓库均不得包含真实 Key。

本轮已在 Codex 内置原生 MCP 客户端中发现五个工具并完成只读查询；当前聊天直接工具列表的挂载状态需另行检查，不能据此声称所有新会话都已加载。后续记录实际调用通道，不以自制 HTTP 请求冒充原生 MCP 工具。

## 6. 博客空间 3D 开场恢复

当前问题已定位：[BlogSpacesPage](../src/components/BlogSpacesPage.tsx) 使用普通卡片目录，未挂载仍保留的 [BlogSpaceGallery](../src/components/BlogSpaceGallery.tsx)。这是目录装配变化，不应通过清空用户数据、重建成员或替换作者博客来解决。

两版都必须恢复可用的 3D 开场，而非只为 Pro 版提供该能力：

- 共享公开空间清单、成员与内置示例的区分、预览地址及打开完整博客的动作。
- 保留现有原创空间构图、选中聚焦、返回总览、键盘操作和真实页面预览要求。
- 公开版审查并复用权属明确的自写几何与预览逻辑，动效改用原生动画或核验后的开源实现。
- Pro 版可以采用经授权的视觉组件，但应证明它能承载真实博客预览；纯图片球面画廊不能未经验证就替代现有交互。
- 减少动态、触屏、WebGL 不可用或预览失败时提供可操作的普通目录；不以空白画布阻止访问博客。
- 继续保留同源与 sandbox 边界、公开预览允许列表、两路并发预算、缓存、超时和销毁清理。

当前画廊依赖 GSAP；仅重新挂载旧组件不构成公开版的许可审查完成。字体、模板预览和内置人物资料也需要按真实来源保留说明。

## 7. 分阶段实施顺序

各阶段以具体产物和验收为完成依据。阶段 0 结束后先进入选材与权利核查，不在文档任务中顺带重构全站。

| 阶段 | 主要工作 | 交付物与完成条件 |
| --- | --- | --- |
| 0：本轮文档 | 确定两版范围、共享边界、许可、实施与验证顺序 | 本计划、任务表和文档入口；没有新增素材解锁或运行时代码变更 |
| 1：素材与现状盘点 | 核查既有 RBP、React Bits、GSAP 及其他拟采用材料；用 MCP 给出 Pro 候选 | 逐项来源与权限清单，用户确认的候选；授权不清的素材不进入实施 |
| 2：隔离与最小骨架 | 确定公开 UI 自写代码许可；建立私有工作区与最小视图契约 | 一个页面完成公开／私有装配验证；公开构建无私有依赖；此处只是可运行骨架 |
| 3：Pro 版先做 | 按用户确认的素材逐项验证、领取并在私有仓库适配 | 先验收首页、社区、博客 3D 开场，再扩展资源与其他平台外壳；不影响作者内容 |
| 4：公开 UI 完整实现 | 按共同产品需求原创设计，使用核准开源组件 | 与 Pro 版业务能力一致的完整公开 UI；不从 Pro 源码改名、移植或让 AI 改写后转公开 |
| 5：两版对照验收 | 验证共享行为、移动端、权限、性能、可访问性和材料隔离 | 真实的测试与截图记录，许可清单和阻塞项全部有结论 |
| 6：构建与交付 | 公开版源码独立构建；Pro 版私有构建并核验成品交付权利 | 干净环境可运行的公开版；符合授权范围的 Pro 部署产物及私有操作文档 |

阶段 3 和阶段 4 在视觉实施上按 Pro 先、公开 UI 后进行；阶段 2 先提供最小公开骨架是防止两版隔离导致公开仓库不可构建，不是提前完成第二套视觉。

## 8. 每个页面的实现与验收

每次只推进一个可核对的页面或公共能力，按以下顺序完成：

1. 列出实际内容、用户动作、语言与主要状态，确认使用的素材和许可。
2. 展示有来源的候选或原创设计预览，确定本页布局与动效。
3. 实现装配与交互，保留既有业务行为和作者内容。
4. 验证适合本次变化的单元／HTTP 回归、类型检查和生产构建。
5. 在桌面与手机检查实际页面，覆盖键盘、减少动态、加载失败和空状态。
6. 检查差异、来源与分发边界；更新实现文档后，再提交属于本次工作的文件。

不把单张截图、模板预览或历史测试数量当作当次功能完成。公开版与 Pro 版应使用同一组明确标记的测试资料，不复制生产数据库或真实用户上传做公开示例。

## 9. 两版共同的发布验收

### 9.1 功能与数据

- 同样的登录、账号隔离、查询、收藏、关注、投稿、评论与审核结果。
- 同样的博客编辑、私有草稿、公开快照、修订和下线语义。
- 切换 UI 不重置账号、数据库、上传、发布状态或作者主题。
- 服务端继续执行权限检查，不能只依赖 UI 隐藏按钮。

### 9.2 公开版可独立运行

- 在未安装任何 Pro 文件、私有包、开发者本机链接及 uiX 凭据的干净环境中，按公开文档安装、初始化、构建并启动。
- 常规注册、邮件等运行配置按现有部署指南提供；这些配置不应被混同为素材库授权凭据。
- 实际打开首页、社区、资源、博客 3D 开场、普通博客及编辑器，验证所需资源没有私有地址依赖。
- 新公开 UI 的第三方代码、字体与图片有对应版本的许可及必要署名；未审查的旧适配部分不得被悄悄标记为已清理。

### 9.3 Pro 版不向公开仓库泄露材料

- 审查公开源码、生成文件、测试夹具、快照、日志、缓存、源码映射、构建附件和文档；不包含受限素材正文或可复用交付包。
- 公开包不依赖 Pro 文件存在，私有包不被公开流水线误上传。
- Pro 完整应用镜像是否允许向第三方交付须有对应授权结论；默认仅作维护者私有构建和部署，不预先发布镜像。
- 浏览器仍会收到应用运行需要的 JS/CSS，不能把“UI 闭源”描述为客户端代码绝对不可查看。

## 10. 交付、版本与回滚

公开版继续维护独立可运行的源码和部署说明。Next.js 可使用 standalone 等方式生成运行产物，但应包含必要的服务端文件、静态资源与公共素材；这只是技术打包方式，不代表素材获准再分发。

私有版固定所用公开核心提交，记录 UI 适配版本、依赖锁文件和私有材料版本。两版发布说明分别列出共享逻辑变化与视觉变化。若未来开放 Pro 成品交付，另行核对具体接收人、应用用途、部署方式与上游授权。

回滚优先恢复上一份已验证 UI 与兼容的共享核心，不回滚或清空真实用户数据。涉及数据结构变化时另出迁移与恢复方案；不能因为换肤顺带修改数据库。

公开仓库内经验证的改动按 [AGENTS.md](../AGENTS.md) 同步到既有 GitHub 与 AtomGit 镜像。私有 Pro 源码不进入这一公开同步流程。创建私有远端、正式部署、对外发布镜像及改写 Git 历史不因本计划自动执行。
